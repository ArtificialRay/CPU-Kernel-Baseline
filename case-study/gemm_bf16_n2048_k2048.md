## 1. Reference-scalar vs baseline-llamacpp-arm: measured near-parity, and why

Unlike the ncnn conv definitions, this run gives a **direct measurement**, not just an
inference from source code: **v1 is byte-identical to `reference-scalar-kernel.cpp`**
(`agent-runs-nanobot/gemm_bf16_n2048_k2048/reference-scalar-kernel.cpp` vs `v1.cpp` — same
scalar `bf16_to_f32` + triple-nested loop, submitted unmodified at turn 3). Its own
measured result against the baseline (`trajectory.jsonl` turn 2):

```
time_speedup_geomean = 1.4660, cycle_speedup_geomean = 1.4653
```

So **reference-scalar is essentially at parity with baseline-llamacpp-arm** (candidate
≈1.47× faster, not orders of magnitude apart in either direction). This confirms, with an
actual measurement, what the ggml source predicts structurally: `ggml_vec_dot_bf16`
(`ggml/src/ggml-cpu/gemm_gemv/vec.cpp:139-262`) branches on `__AVX512BF16__`,
`__AVX512F__`, `__AVX2__`/`__AVX__`, `__riscv_zvfbfwma`, and
`__POWER9_VECTOR__`/`__VXE__`/`__VXE2__` — there is no `__ARM_FEATURE_*` branch in this
function at all (contrast `ggml_vec_dot_bf16`'s neighbor `ggml_vec_dot_f16` at line 264,
which *does* have an explicit `#if defined(__ARM_FEATURE_SVE)` branch). On AArch64 every
call falls through to the scalar tail:

```cpp
// ggml/src/ggml-cpu/gemm_gemv/vec.cpp:257-260 — the only code that runs on ARM
for (; i < n; ++i) {
    sumf += (ggml_float)(GGML_BF16_TO_FP32(x[i]) * GGML_BF16_TO_FP32(y[i]));
}
```

`llamafile_sgemm`'s own `GGML_TYPE_BF16` case
(`ggml/src/ggml-cpu/gemm_gemv/llamafile/sgemm.cpp:3766-3826`) likewise has no ARM branch
and returns `false`, so `ggml_compute_forward_mul_mat`
(`ggml/src/ggml-cpu/ggml-cpu.c:1235-1412`) falls back to its generic chunked path calling
`ggml_vec_dot_bf16` once per `(row, col)` — the same algorithmic shape as
`reference-scalar`. The small residual 1.47× is consistent with ggml's per-call
`ggml_context`/`ggml_cgraph` construction overhead (see §2) rather than any ARM
vectorization on the baseline's side, since there isn't any.

## 2. baseline-llamacpp-arm's own bottlenecks

**No SIMD for bf16 on ARM** (established in §1 with a direct measurement, not just
inference) is the dominant factor. Two secondary costs, visible in
`bench-trace/solutions/llama.cpp/baseline-llamacpp-arm/gemm/gemm_bf16_n2048_k2048.json`
`kernel.cpp`:

- **Full `ggml_context`/`ggml_cgraph` setup runs inside the timed region on every call**
  (`ggml_init`, two `ggml_new_tensor_2d`, `ggml_new_graph`,
  `ggml_build_forward_expand`) — there is no persistent pipeline amortized across the 24
  workload evaluations, unlike ncnn's `create_pipeline`. The file's own comment says so
  directly: *"Like the ncnn baseline (layer create + create_pipeline + forward per entry
  call), the whole ggml context/graph setup runs inside the timed region."*
- **`ggml_graph_compute_with_ctx(ctx, gf, /*n_threads=*/1)` is hardcoded single-threaded**
  in the baseline's own binding — whatever thread-distribution machinery exists in
  `ggml_compute_forward_mul_mat` (`ggml-cpu.c:1372-1412`) buys nothing here.

## 3. Why the candidate wins by up to ~254× — and a methodological flag the numbers themselves surface

`time_speedup = baseline_time / candidate_time`. v25 (peak) is measured at **253.90×**
faster than baseline; even the weakest fully-optimized version (v6, pre-threading) is
**35.70×** faster. Both facts need explaining, and the run's own `cycle_speedup` numbers
point to two genuinely different mechanisms behind them.

### Step 1 — v1→v6: SIMD width and a real correctness bug, single-threaded throughout

- **v1→v2 (1.47×→14.56×)**: replaces the scalar `bf16_to_f32`-then-multiply loop with
  `svbfdot_f32` (`v2.cpp:43-46`) — SVE's native bf16 dot instruction, 16 bf16 lanes
  packed into 8 fp32 partial sums per instruction. `time_speedup ≈ cycle_speedup` here
  (ratio 1.01, table above) — entirely consistent with a single-threaded SIMD-width win,
  the same signature seen in every other conv2d case study in this repo.
- **v3→v4 (real bug)**: v4 attempts to tile M for cache reuse (`v4.cpp:15-146`) but its
  own comments admit the implementation is unfinished — *"We only computed n and n+1
  above; need n+2 and n+3 separately... this approach is getting complex, simplify"*
  (`v4.cpp:93-96`) — and the M-tiled fast path only ever consumes `vb0a/vb0b` and
  `vb1a/vb1b` while `b2`/`b3` are loaded but never fed into an `svbfdot_f32` in that path.
  This produced `status: INCORRECT_NUMERICAL` at turn 12
  (`max_abs=56.59, max_rel=26350, matched_ratio=0.669` — nearly a third of output
  elements wrong). **The agent correctly detected this, did not submit v4, and reverted**:
  v5 (`v5.cpp:19-92`) drops the M-tiling entirely and returns to a straightforward
  per-row loop with 2 accumulators per N-lane for `bfdot` latency hiding — simpler than
  v4, and *slower* than v3 (14.69× vs 15.36×) — a deliberate correctness-over-performance
  trade after a caught bug, not an oversight.
- **v6 (35.70×)**: a genuine 4×4 register tile (`v6.cpp:22-133`) reusing each loaded B row
  across 4 A rows before moving to the next N tile — the first version that actually
  amortizes B loads across M, cleanly explaining the ~2.3× jump over v5 with `ratio` still
  ≈1.02 (single-threaded).

### Step 2 — v10 onward: `time_speedup` and `cycle_speedup` diverge sharply, and the divergence lines up exactly with `#pragma omp parallel for`

This is the central finding of this section. The `time speedup / cycle speedup` ratio
column in the header table is essentially **1.00–1.02 for every version through v9**
(all single-threaded) and then **jumps to 1.4–3.5+ starting at v10**, the first version
to add:

```cpp
// v10.cpp:101-102
#pragma omp parallel for schedule(static)
for (int m = 0; m < M; m += MT) {
```

and stays elevated for every subsequent version (v11–v43 all include `#include <omp.h>`
and a `#pragma omp parallel for`). If `cycle_speedup` reflects cycles actually consumed
and `time_speedup` reflects wall-clock latency, `time_speedup ≫ cycle_speedup` is the
textbook signature of work being spread across multiple execution contexts: total cycle
count doesn't fall proportionally, but wall-clock time does, because several threads are
burning cycles concurrently rather than one thread burning them serially.

**This deserves a direct flag**, not a quiet pass-through, because it appears to
contradict the benchmark harness's own stated design. `bench/config.py:25` sets
`DEFAULT_CPU = 0`, and `bench/runtime/timing.py`'s `pin_to_cpu` calls
`os.sched_setaffinity(0, {cpu})` — `pid=0` pins the **calling process** (whose mask new
threads normally inherit at creation, including a lazily-spawned OpenMP worker pool) to a
single core. `mcp_app/agent_tools/ops.py:115` (`env = _current_environment(cpu_pinned=cfg.cpu)`)
confirms this run's evaluation tool resolves `cfg.cpu` from the same
`BenchmarkConfig`/`EvalConfig` defaults and feeds it through the same `bench/runtime`
timing path used by the local harness — there is no `gemm`-specific override for `cpu` in
`bench/config.py`'s `DEFAULT_OP_TYPE_CONFIG` (only tolerance fields are overridden
per-op-type). On paper, this evaluation should be single-core, and OpenMP threads spawned
inside it should not be able to run concurrently on separate physical cores.

The measured numbers say otherwise: not just the abrupt v9→v10 jump, but the entire
shape of the later exploration. v10 parallelizes over `M` in chunks of `MT=4`
(`v10.cpp:102`) — for the smallest tested M (M=1), that loop has exactly one chunk, i.e.
**zero parallel work to distribute**, yet the *aggregate* geomean still jumped
2.7× (35.70×→98.06×) across the full 24-workload set. By v14, the agent switches to
`collapse(2)` over both M- and N-chunks (`v14.cpp:110`), and by v25 to parallelizing over
**N**-tiles-of-8 instead of M (`v25.cpp:135-136`, `N_tiles8 = N/8 = 256`) — explicitly
because, per v25's own header comment, *"parallelize over N tiles... process all M rows
per tile... this gives more parallelism for large M"* (`v25.cpp:4-7`). Decoupling the
parallel grain from the tiny, workload-dependent M axis and pinning it to the large,
constant N axis is a legitimate, well-reasoned adaptation to this problem's shape — but
it is only a meaningful thing to optimize *if OpenMP threads are actually running
concurrently on more than one core*. If they weren't, tuning parallel-loop granularity
would have no effect on wall-clock time at all.

**Net assessment**: the evidence (systematic `time/cycle` ratio jump exactly at the first
`#pragma omp`, and later versions' tuning effort concentrated on parallel-loop shape in
ways that only pay off under real concurrency) points toward genuine multi-core execution
happening during these evaluations, in tension with the harness's apparent single-CPU-pin
design. This case study cannot resolve *why* from static source inspection alone — it
would need a runtime check (e.g., have a kernel version log `sched_getaffinity(0)` and
each OpenMP thread's `sched_getcpu()`) to confirm whether the affinity pin is actually
taking effect for this run's execution environment. Until that's checked, **the ≥98×
numbers from v10 onward should be treated as measuring "candidate kernel, however many
cores it can get" against "baseline, hardcoded to 1 thread" — not an apples-to-apples
single-core comparison** — regardless of whether that reflects a harness bug or an
intentional (but undocumented) allowance for candidate-side threading.

### Step 3 — Remaining SIMD-side changes (v10→v25) on top of the threading effect

Independent of the threading question, cycle_speedup itself (a threading-orthogonal proxy
for single-thread efficiency, if the counter is per-thread as assumed) also climbs
steadily across this stretch: 47.44 (v10) → 58.35 (v14) → 77.66 (v25) — a genuine ~1.6×
improvement from IPC gains (`ipc_mean` 3.67→3.83→3.85, table above) as tiling shifted from
plain 4×4 (v10) to two 4×4 sub-tiles per 8-wide N chunk with more register-resident
accumulators (v25, `compute_4x4_tile` + a second call over `n+4`, `v25.cpp:158-159`).

## 4. Hardcoded parameters — corrected against v25 (peak)

As with the earlier (stale-run) analysis, **N=2048/K=2048 are legitimately given as
`constexpr`** by the harness (`gemm.h`, same contract as conv2d's Kh/Kw) — not an agent
shortcut. M is handled generally in every submitted version via a fallback remainder
loop. That conclusion is **unchanged**. What *is* new in v25 relative to the earlier
(stale-run) versions is a real regression in defensive coding:

**v25 has no N-tail handling at all — a correctness gap, currently silent only because
every `gemm_bf16` sibling N happens to be a multiple of 8.**

```cpp
// v25.cpp:126-136
const int NT8 = 8;
const int N_tiles8 = N / NT8;          // integer division — drops any remainder
#pragma omp parallel for schedule(static)
for (int nt = 0; nt < N_tiles8; ++nt) {
    int n = nt * NT8;
    ...                                 // only ever touches n in [0, N_tiles8*8)
}
```

There is no loop, scalar or otherwise, for `n` in `[N_tiles8*8, N)`. Contrast this with
v1, v6, and v10, which all had an explicit `for (; n < N; ++n)` (or equivalent) remainder
loop. For N=2048 this is invisible (`2048 / 8 == 256` exactly, `2048 % 8 == 0`), and it
happens to also hold for every other N in the `gemm_bf16` family (1024, 1408 — both
multiples of 8), so it does not currently misbehave on any defined sibling. But it is a
strictly worse guarantee than the versions that preceded it in the same run: v25 would
silently leave the last `N mod 8` output columns **unwritten** (not just slow — wrong) on
any N not divisible by 8.

K-tail is likewise unguarded in v25's SVE helper functions (`compute_4x4_tile`,
`compute_1x8_tile`, `compute_1x4_tile` all loop `for (k=0; k+vl<=K; k+=vl)` with no
post-loop scalar remainder) — holds for K ∈ {1024, 1408, 2048} (all multiples of 16) but
is, again, an unstated assumption rather than a checked one.

### Summary

| Parameter | Hardcode type | Effect of changing |
|-----------|---------------|---------------------|
| N=2048, K=2048 | Not hardcoded — given as `constexpr` by the harness | N/A — intended API |
| M (var) | Not hardcoded | Fully generalized in every submitted version, including M=1 |
| **N % 8 (v25)** | **Correctness bug (dormant)** | **No tail loop at all** — silently drops the last `N mod 8` output columns; holds only because every current `gemm_bf16` sibling N is a multiple of 8 |
| K % 16 | Implicit assumption, unguarded | Holds for all current `gemm_bf16` K values; would over-read on a K not divisible by 16 |
| `#pragma omp parallel for` (v10+) | Not a hardcode, but a methodology question | See §3 Step 2 — the measured `time_speedup` for every OpenMP version may reflect multi-core execution the benchmark's single-CPU-pin design did not intend to allow; needs runtime verification, not a source-level judgment |
